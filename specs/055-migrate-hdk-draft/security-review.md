## Boundary and claims

The local profile uses published BIP39, RFC 5869, RFC 9180 P-256 parent generation, the scalar mapping and child-key relation in Section 7 of the pinned draft, RFC 8032 Ed25519 and FIPS 204 ML-DSA seed generation. The draft uses an ephemeral per-issuance X25519 `shared_secret` and assumes an accepted secure-area parent; this profile substitutes a deterministic RFC 5869 secret bound to the full credential ID and a deterministically provisioned software parent. Its label/identity/root composition and changed child inputs are application policy and have their own custom-protocol review obligation. It implements no issuer protocol or X25519 exchange and inherits no security analysis by merely citing a related construction.

The threat boundary includes encrypted recovery storage, software root/parent/seed handling, identifier and profile input, provider adapters, user-authorized signing, current event persistence and recovery. Non-exportability, issuer assurance, malware resistance after plaintext root compromise, complete mnemonic-only recovery, and forensic JVM erasure are not provided by this design.

## Findings and required controls

| Finding | Required control / evidence |
| --- | --- |
| Root compromise reconstructs every branch. | State this explicitly. Different labels separate purposes, not authority against possession of PRK/recovery material. |
| A child private scalar plus its factor reveals the parent by inversion. | Keep factors and child/private bytes operation-local; do not claim independent child-compromise containment. |
| Complete identifiers prevent the old shortened-input collapse. | Freeze distinct collision fixtures; describe cryptographic collision resistance, not universal mathematical uniqueness. |
| One current profile must survive reconstruction. | Check algorithm/profile pairs at current boundaries; round-trip SQL/event/snapshot identity. No legacy registry or upgrade logic. |
| Root getters currently alias caches. | Copies under synchronized publication/clear, consumer `finally` cleanup, and fakes obeying the same ownership contract. |
| Cache clearing cannot erase in-flight copies or interrupt an already admitted synchronous provider call. | Apply the lifecycle contract's owner/generation policy: fence/cancel work, reject new signing admission, discard stale in-flight results, and erase operation copies. Do not claim forced interruption or physical reversal of provider work. |
| Private mnemonic `String`/`List<String>` values are current application-owned violations. | Replace them with mutable crypto processing and mutable UI owners. The display exception applies only to unavoidable existing platform presentation calls. |
| BC/JCA/ICU/runtime create internal copies, and `BigInteger` is not erasable. | Audit exact adapters, object lifetimes and exposure. Keep immutable provider objects confined to the shortest cryptographic call and never in application models/caches; use mutable application buffers and erase them. Do not claim array zeroing erases dependency/runtime copies. |
| Provider key equality and malformed point/scalar inputs can hide identity errors. | Validate canonical representation/ranges/correspondence and reject mismatch before signing. Remove public-key repair. |
| Fixed HKDF salt conflicts with current blanket salt wording. | Apply the proposed published-KDF clarification while retaining fresh random nonce/IV requirements. |
| Existing hmac-secret behavior is an independent simplified implementation. | Update root-copy cleanup only; do not present this feature as completing CTAP extension interoperability. |

If the exact provider boundary cannot be justified under the existing mutable-owner rule, change the adapter or obtain the specifically required amendment through governance. Do not silently classify application-created immutable secrets as external copies. This audit is an implementation deliverable, not permission to waive cleanup.

## Ownership audit inventory

| Secret | Application owner | Required terminal action |
| --- | --- | --- |
| Mnemonic, entropy, checksum/index work, normalized/UTF-8 buffers | Generator/provider/import operation or existing UI owner | Erase replaced/terminal mutable buffers, including failed validation, cancellation and hidden/disposed UI state. |
| BIP39 `S`, root extraction intermediates | Wallet initialization | Erase after extraction/provisioning; never publish partially initialized cache. |
| Cached PRK and parent scalar | Provider's bounded current wallet session | Erase on replacement/end/pressure; copy under cache synchronization. |
| Root copies consumed by signing, events, DB, HMAC and initializer | Each consumer operation | `finally`, even availability/null-check paths that obtain a copy. |
| Parent input and RFC 9180 candidate bytes | Parent derivation operation | Erase every rejected candidate, labeled PRK and working array, including sampler exhaustion. |
| Credential seeds/local secret | Current key operation | Erase after public generation or signing, on every exit path. |
| Factor/hash/child private bytes/private encodings | HDK/signing operation | Scoped result plus outer `finally`; never persist or log. |
| Event/snapshot encryption keys and plaintext serialization buffers | Existing current store operation | Erase owned key/plaintext copies after encryption/decryption or failure. |

Provider-managed key objects and immutable arithmetic values require a precise boundary register, not a claim of controllable physical erasure. The current normalizer's mutable destination avoids adding application-owned secret Strings but does not prove ICU internals are erasable.

## Verification conditions

1. Independent fixture engine matches published HKDF/parent vectors before producing local expected bytes.
2. Current P-256 inputs, non-zero scalar mapping, private/public relationship, hierarchy composition and index boundaries match fixed independent results.
3. Ed25519 and ML-DSA seed import produces valid expected keys/signatures without the custom random generator.
4. Real production wallet creation/restart/persistence works; a duplicated test-only wallet implementation is not accepted as proof.
5. Failure/cancellation tests assert erasure of owned buffers and safe cache publication without mutating provider or caller-owned storage.
6. Current registered-key mismatch rejects signing and never schedules a repair or writes a new public key.
7. Static checks, configured Compose/device lifecycle/Keystore evidence, transaction rollback, Tier 1/Tier 2/repository coverage floors and latency/binary/memory budgets satisfy the plan. Test foreground/HID overlap, each mandatory memory level, last-owner cleanup and same-wallet lazy reinitialization.

Implementation should append its concrete reviewed findings and evidence to a dated implementation/security record. Independent reviewers can use [the prepared review packet](security-review-packet.md). No approval is implied by this planning assessment.
