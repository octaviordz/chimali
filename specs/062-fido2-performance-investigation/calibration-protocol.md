## Claim and scope

The calibration claim is limited to the designated ASUS_AI2302 / Android 15 API 35, the exact target and test APK/source/config/query identity recorded for the run, and the two predeclared conditions: quiet and documented synthetic CPU load. It is a probabilistic engineering tolerance, not a guaranteed maximum and not a population-wide claim.

For each component (`C` clock/trace alignment and `H` nonnegative paired instrumentation overhead) and each condition, require at least 99% coverage with 95% familywise confidence across the four component/condition claims. The allowance is `u = C + H`. The existing registration sensitivity calculation at `1u` and `2u` remains unchanged.

## Independent sampling unit and workload

One sampling unit is a complete, separately started instrumentation process **and its own Perfetto trace session**, with a fresh process-session UUID and one fixed condition. Do not treat multiple measurements from one process/trace session as independent. Each independent session has one separately labeled marker warmup and one control warmup, then exactly one measured clock/marker bracket and one alternating enabled/disabled hook-control pair. It also records 1,000 consecutive clock-increment probes and the declared scheduler/clock health data. The one measured clock envelope and one nonnegative paired control difference are the independent outcomes for that session; the historical candidate limits were computed from individual observations of these same quantities.

Collect 437 independent sessions under quiet conditions and 437 under the documented CPU-load condition. Randomize the order of the 874 sessions with a retained pre-generated schedule; do not change assignments after observing results. A session that lacks complete records or fails any declared trace-health check fails the holdout; do not replace it or silently exclude it. Stop on the first trace-health failure or candidate exceedance. Keep every attempted session and its disposition.

Quiet means no synthetic load worker. CPU load means the runner's documented deterministic synthetic CPU worker runs during measurement and stops before session completion. No RP, Bluetooth, credential, account or user data activity is part of calibration.

## Statistical acceptance

For each session compute:

- `C_session = bracket_width + marker_distance_outside_bracket` for its one uniquely paired measured marker.
- `H_session = max(0, enabled_ns - disabled_ns)` for its one measured paired control.

For a particular holdout, use only the candidate limits frozen in that run's predeclaration. All 874 sessions must be trace-healthy and, in each quiet and CPU-load stratum, all 437 `C_session` and 437 `H_session` values must be at or below their respective frozen limits. The Cal21/22 numerical limits in the historical section above are not current T017 limits.

With zero exceedances among `n` independent session observations, the exact one-sided binomial upper limit on exceedance probability at per-claim confidence `1 - alpha` is `1 - alpha^(1/n)`. For 99% coverage, allocate familywise alpha `0.05` across four claims using Bonferroni (`alpha=0.0125` per claim). `n=437` with zero exceedances gives an upper exceedance probability below 1% for every claim and at least 95% familywise confidence. Each statistical observation is generated by a fresh process/trace session, so no adjacent within-session bracket or paired-control observations are counted as independent; the 1,000 clock increments are diagnostic only and are not part of the sample count.

One exceedance, incomplete session, trace-health failure, mismatch in frozen identity or missing scheduled session fails the holdout. There is no post-hoc expansion or retry. A failure leaves calibration incomplete and requires a newly approved, predeclared policy before any further capture. A pass freezes the approved `u` and permits T008 verification to continue; it does not itself collect or qualify baseline registrations.

## Identity, capture and retention

Use the actual instrumented `shrunkDebug` APK intended for baseline and the calibration test APK exercising the same production hooks, context, lifecycle and event sink. Record device/OS, target/test APK hashes, source fingerprint, config and SQL hashes, test-runner source identity, process-session UUID, randomized schedule and trace filename for every unit. Any changed target APK, hook implementation, runner semantics, trace config or query requires a fresh identity and a newly declared holdout.

Install the test APK before tracing. Start one Perfetto session for each scheduled unit, run exactly one instrumentation invocation for that condition, stop and query the trace, validate all requested scheduler families and health counters, normalize the measured marker timestamp, compute the one-session clock/control observations and retain secret-free CSV/health/report rows. Delete each raw system-wide trace after validation and secret review. Preserve the schedule and every completed, failed or interrupted session record. Use the checked-in [calibration query](artifacts/f062-calibration-trace-query.sql) and the reproducible [percentile analysis script](artifacts/f062-calibration-percentile-exploration.ps1) only for historical comparisons; the new holdout acceptance uses one independent clock/control observation per session.

Do not start registration baseline collection unless all 874 independent holdout sessions pass, the final target APK/source/config/query identity matches the baseline declaration, trace health is complete, and `u` is frozen in the evidence record. A calibration pass validates only the stated empirical tolerance under the specified conditions; it does not prove the exact absolute error of an individual future observation.
