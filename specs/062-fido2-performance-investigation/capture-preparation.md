### T028 bounded feasibility conclusion (2026-10-30)

**Clock path assessed:** Perfetto documents that Linux/Android ftrace events use `CLOCK_BOOTTIME` and that Trace Processor uses clock snapshots to convert different event clock domains to the trace clock. The preflight contained snapshots for BOOTTIME, MONOTONIC, MONOTONIC_RAW, REALTIME and coarse variants. The run config now explicitly selects BOOTTIME as its primary trace clock. For a future valid run, analyze only Trace Processor-normalized timestamps from one trace and retain that run's clock snapshots and primary trace-clock metadata; reject conversion paths that are absent, non-monotonic or flagged by trace health. This provides a defensible *conversion procedure*, but not a numeric conversion-error bound for every event.

**Resolution assessed:** Android documents `SystemClock.elapsedRealtimeNanos()` as nanoseconds since boot, monotonic and inclusive of sleep. The API contract does not state a maximum clock read error/resolution for the target build/device. Reporting nanosecond units does not by itself establish one-nanosecond accuracy. The accessible device check of `/sys/kernel/tracing/trace_clock` reported `[local]`; this is not a measurement of BOOTTIME resolution or an API accuracy guarantee.

**Perturbation assessed:** Android's `Trace.beginAsyncSection`/`endAsyncSection` contract specifies matching marker name/cookie behavior, but no maximum call duration or timestamp error. The measured lookup also runs coroutine context switching and fixed log emission around lifecycle events. No target-device event trace was successfully captured to measure these paths. A same-device timing distribution, even if captured, would be observed samples rather than an independently guaranteed upper bound; the contract excludes using a sampled maximum as a worst-case bound. No platform or build guarantee was found that bounds scheduler perturbation caused by the instrumentation.

**Disposition:** T028's bounded feasibility study is complete, but its required numeric error bound `e` cannot be established from the documented guarantees or available target-device evidence.
