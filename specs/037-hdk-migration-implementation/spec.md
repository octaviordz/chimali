# Feature Specification: HDK Migration Implementation

**Feature Branch**: `037-hdk-migration-implementation`  
**Created**: 2026-05-14  
**Status**: Draft  
**Input**: User description: "Goal to only use Hierarchical Deterministic Keys algorithm, and procedures from https://datatracker.ietf.org/doc/html/draft-dijkhuis-cfrg-hdkeys-06, remove all BIP-32, and BIP-44 path related HDK code. ## User Scenarios & Testing *(mandatory)*

### User Story 1 - Secure Post-Quantum Key Derivation (Priority: P1)

As a security-conscious user, I want my post-quantum keys (ML-DSA) to be derived using the modern HDK standard instead of legacy BIP-32, so that the application follows the latest IETF cryptographic drafts.

**Why this priority**: Core security requirement. Replacing legacy derivation with HDK is the primary goal of this feature.

**Independent Test**: Verify that calling `getPqChildSeed()` twice with the same master seed returns the same 64-byte result, and that this result is different from the legacy BIP-32/85 derivation result.

**Acceptance Scenarios**:

1. **Given** a valid 32-byte master seed, **When** `derivePqChildSeed` is called, **Then** it must return a deterministic 64-byte child seed derived via HDK `DeriveSalt` and HMAC-SHA512 expansion.
2. **Given** the same master seed, **When** compared against legacy BIP-32/85 derivation output, **Then** the result MUST be different (clean break).

---

### User Story 2 - BIP-39 Mnemonic Continuity (Priority: P1)

As an existing user, I want my BIP-39 mnemonic phrase to remain the root of all my keys, so that I don't have to generate a new recovery phrase.

**Why this priority**: Critical for user experience and continuity. The "clean break" only applies to derived keys, not the recovery phrase itself.

**Independent Test**: Verify that importing an existing BIP-39 mnemonic still produces the same master seed as before.

**Acceptance Scenarios**:

1. **Given** a known BIP-39 mnemonic and passphrase, **When** the master seed is generated, **Then** it MUST match the seed generated by previous versions of Chimali.

---

### User Story 3 - Full BIP-32 Removal (Priority: P2)

As a developer, I want all legacy BIP-32/44 code removed from the codebase, so that the cryptographic implementation is lean and strictly follows the HDK standard.

**Why this priority**: Reduces technical debt and maintenance overhead. Ensures no accidental reuse of legacy derivation.

**Independent Test**: Search the codebase for "BIP-32", "BIP-44", "ckdHard", and legacy constants; verify zero functional occurrences remain in the data/crypto layers.

**Acceptance Scenarios**:

1. **Given** the `WalletMasterSeedProvider.kt` file, **When** audited after implementation, **Then** no BIP-32 constants or logic (like `ckdHard`) should exist.

---

### Edge Cases

- **Boundary condition**: Master seed size. System handles 16-byte, 32-byte, and 64-byte master seeds (BIP-39 seeds are 64 bytes; HDK typically uses 32 bytes of entropy).
- **Error scenario**: `HdkManager` unavailability. System fails gracefully or throws a clear cryptographic exception if the HDK implementation is missing or misconfigured (though it's bundled in `core/security`).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST use the HDK `DeriveSalt` primitive (§2.4 of `draft-dijkhuis-cfrg-hdkeys-06`) for PQ branch isolation.
- **FR-002**: System MUST use a domain-separated context string `"PQ_ML-DSA_Branch"` for DeriveSalt.
- **FR-003**: System MUST expand the 32-byte `DeriveSalt` output to 64 bytes via `HMAC-SHA512` using key `"chimali_pq_seed_v1"` and the derived salt as the sole message input.
- **FR-004**: System MUST remove the `ckdHard()` and legacy `derivePqChildSeed()` implementations from `WalletMasterSeedProvider.kt`.
- **FR-005**: System MUST remove all 14+ BIP-32/85 related constants and logic from the FIDO2 crypto layer.
- **FR-006**: System MUST preserve the `Bip39MasterSeedGenerator` implementation and logic unchanged.
- **FR-007**: System MUST update the Project Constitution (§II Master Seed Architecture) to reflect the removal of BIP-32 and adoption of HDK DeriveSalt.
- **FR-008**: System MUST annotate historical documentation (changelogs, BRD) with notes about the BIP-32 supersession.

### Key Entities *(include if feature involves data)*

- **Master Seed**: The root of all cryptographic material, derived from BIP-39 mnemonic.
- **HDK Salt**: Deterministically derived 32-byte value used for sub-branch isolation.
- **PQ Child Seed**: 64-byte entropy source for ML-DSA key pair generation.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% removal of functional BIP-32/BIP-44 logic and constants from the core cryptographic path.
- **SC-002**: Passing KAT (Known-Answer Test) for PQ branch derivation using the specified context string and expansion HMAC.
- **SC-003**: 0% regression in BIP-39 mnemonic to master seed derivation.
- **SC-004**: 100% of internal tests pass, including new assertions for PQ/ECDSA branch independence.

## Assumptions

- **Clean Break**: Existing PQ-based credentials will be rendered invalid and will not be migrated. This is acceptable as the project is in a pre-production state.
- **HDK Implementation Availability**: The system assumes access to a compliant implementation of the HDK-ECDH-P256 specification.
- **Deterministic expansion**: A cryptographic expansion function (HMAC-SHA512) is required to produce the 64-byte seed from the 32-byte derived salt.
- **Dependency**: The FIDO2 cryptographic layer requires access to the HDK management service.
