# Contract: Cleanup Boundaries and Assessment Evidence

**Status**: Phase 1 design complete for the current [specification](../spec.md). Clipboard policy: fixed 30-second best-effort scheduling, readable ownership check, skip-on-uncertainty, accepted external check-to-clear race and prepublication sensitive marking. Initial/post-design gates pass. Implementation and release security acceptance remain pending. No external network API is introduced.

## Sensitive operation inputs and internal interface

The internal `ClipboardManagerService` will accept a fixed non-identifying label and a borrowed caller-owned mutable password-operation buffer. The caller owns that copy through return/cancellation and erases it in `finally` plus never-started completion handling; the adapter erases any extra mutable conversions and borrows no value beyond publication. Timers/status/receipts never retain text, content hashes, identifying labels or raw errors.

Remove the public `clearDelayMs` parameter. Define one fixed `30_000L` policy value; tests control virtual time rather than changing the product policy. Return `Result<ClipboardCopyReceipt>` for a submitted copy and expose a bounded `StateFlow` snapshot keyed by receipt generation, retaining each receipt's pending or terminal outcome until explicitly acknowledged. Retain `clearClipboard` as an explicit user action with sanitized returned/rejected distinction. Receipts/status are non-secret internal domain types, not a generalized event subsystem.

At most two receipt slots exist, counting pending and unacknowledged terminal outcomes together. Reserve a slot before publication; admit only when a slot is free and no unconfirmed candidate remains pending. Otherwise reject before touching the clipboard. Prepublication admission rejection returns a fixed state-neutral error, creates no receipt/status entry, and is not inserted into the snapshot because doing so would exceed the two admitted-receipt slots or evict another outcome. A single terminal receipt does not block admission when the other slot is free; when both slots are occupied, the caller must handle and acknowledge or record abandonment of enough terminal receipts to free capacity. Each outcome update is atomic and preserves the other slot. Terminal outcomes remain available even when collectors are paused or StateFlow updates are conflated; no unacknowledged outcome is evicted. The responsible caller acknowledges after handling the terminal outcome, or explicitly abandons it after recording its sanitized disposition, releasing the slot. Non-UI callers have the same responsibility. The application-scoped clipboard owner is the fallback receipt custodian: when a caller is permanently disposed, atomically transfer responsibility for its outstanding receipt generations to that owner. The owner retains pending cleanup unchanged, then records a sanitized abandonment disposition for each terminal outcome and releases its slot; if already terminal, it does so at handoff. Serialize handoff with terminal updates and caller acknowledgement so exactly one custodian disposes each receipt. This custodian retains only bounded non-secret receipt state and must not present feedback to a destroyed caller. Temporary collector pauses alone do not constitute disposal. Process termination loses this in-memory state; no completion is invented on restart. Explicit manual clear remains available when slots are full and produces a direct result; pending receipts become terminal with a manual-clear disposition and remain until acknowledged. Acknowledgement removes only its own terminal receipt, never cancels active cleanup. Test two back-to-back completions with a paused collector, acknowledgement, abandonment and capacity backpressure.

Update every implementation, caller and fake together, including iOS source signatures. An Android source change cannot certify iOS runtime behavior; record its source/compile/runtime applicability explicitly. Do not adapt an immutable decrypt owner by merely copying its String into an array; fix or remove that earlier owner based on reachability and evidence.

The existing strict text-boundary policy still applies at each actual conversion. A platform string may exist only at an already permitted exact boundary and be released immediately after the interaction. No seed, key, serializer or provider acquires a password clipboard exception. In particular, eliminate the captured immutable mnemonic in DevTools; an unsupported seed-copy action must fail closed without publishing any clip or claiming it was copied safely.

## Serialized Android clipboard owner

Use one application-scoped owner for copy, manual clear and timer execution. A fresh random non-content token in namespaced description extras identifies each candidate; a local generation fences app callbacks. These are correlation values, not defenses against a malicious app replaying metadata.

Before every sensitive `setPrimaryClip`, set `ClipDescription.EXTRA_IS_SENSITIVE=true` in those extras. The equivalent `android.content.extra.IS_SENSITIVE` key is accepted. Verify both token/flag values and ordering before the platform call. The existing adapter already sets the flag; preserve it while adding identity metadata. Masking is a requested rendering behavior, not access prevention, history erasure or guaranteed expiry. See [Android guidance](https://developer.android.com/privacy-and-security/risks/secure-clipboard-handling).

### Copy transaction

1. Prepare and publish a candidate before replacing accepted local state. On a thrown preparation/publication failure, return a sanitized fixed reason and keep the previous pending generation/timer.
2. After publication returns, record elapsed copy time and the candidate target `copyElapsedMs + 30_000`, then read back description metadata only. A matching candidate token yields a `MetadataConfirmed` receipt; supersede the prior pending copy and schedule the candidate. This confirms metadata visibility, not plaintext-content integrity or lasting availability.
3. If readback is different, missing, denied or unreadable, return an `Unconfirmed` receipt and schedule the candidate without cancelling any previously pending copy. Keep at most two pending non-secret records: the prior copy and the unconfirmed candidate, each with its original due time and guarded token. Reject another copy request before platform publication while an unconfirmed candidate is pending; do not grow a queue or displace either record. A returned-but-ignored write therefore cannot silently remove the previous cleanup obligation. A no-op write whose prior token remains visible is an unconfirmed publication, not a confirmed replacement.
4. Each retained record may attempt only at its own due time, after a matching ownership check; it can never clear the other generation's token. Completion/skip releases that record. Manual clear invalidates both on return; a thrown clear preserves pending records. Process loss discards them. Once the unconfirmed record completes or manual clearing returns, allow another copy only if a receipt slot is also free; terminal receipts retain their slots until acknowledged or abandoned. No secret data is retained in either record.
5. Keep payload conversions out of the scheduled closure. Release permitted platform text after transfer; erase app-owned operation/conversion copies at their terminal boundaries. Rethrow coroutine cancellation; never report cancelled copying as success.

### Automatic cleanup

1. At the scheduled target, or when delayed execution can run, acquire the same owner and recheck generation. An obsolete app callback is a no-op even if cancellation raced its execution. The deliberately retained predecessor of an unconfirmed candidate is still eligible only for its own token and due time.
2. Read `primaryClipDescription` extras only. Matching readable identity permits a clear request; different/missing token skips as replaced/not-owned. Null, denied or malformed metadata skips as ownership-unavailable. Never retrieve or coerce current clipboard text or treat inaccessible metadata as proof of an empty clipboard.
3. Record `ClearRequestSubmitted`, `ClearRejected`, `SkippedReplaced`, `SkippedOwnershipUnavailable`, or `Interrupted`. `ClearRejected` applies only after readable matching ownership allowed the platform clear call and that call threw; it is distinct from unavailable ownership. Record `Interrupted` when the scheduled job is cancelled while state recording remains available. A returned clear or interrupted job is not confirmed removal. End the one-shot attempt/skip and release pending metadata; no indefinite retries, focus polling, wake locks, alarms, services or persistent restart work.
4. Ordinary process death and force-stop can interrupt work; restarted state is Idle and cannot claim past completion. The upfront UI promise is best effort, including these limits. External procedures establish actual interruption rather than expecting a final event from a dead process.
5. Metadata read and clear are non-atomic against other applications. The owner has accepted that remaining race. This never permits app-internal stale-generation clearing or a deliberately blind automatic clear when ownership is unreadable.

### Explicit user clear

Manual clear targets the current entry immediately, without the automatic ownership gate, serialized with copy/timer work. A returned request invalidates pending generation/timer but does not prove removal; a thrown request reports sanitized failure and preserves still-pending work. The timer uses its guarded method rather than calling unconditional manual clear, and does not cancel itself before publishing its outcome.

### Presentation

Use “Password copied. We'll try to clear the clipboard in 30 seconds” only for a `MetadataConfirmed` receipt. For an `Unconfirmed` receipt say “Copy couldn't be confirmed. If copied, we'll try to clear it in 30 seconds.” For admission rejection, use the state-neutral message “Copy is temporarily unavailable. Try again later.” Do not suggest that manual clearing releases receipt slots. The responsible caller must process and acknowledge terminal outcomes or explicitly record their abandonment, including after a paused collector resumes; manual clear remains a separate user action. Explain that interrupted/unavailable cleanup may leave it available, in concise user-facing language. Remove all unconditional “clears in 60s” and “copied safely” claims from affected copy paths. A live presentation owner consumes receipt-correlated status and can report “Clipboard cleanup couldn't be confirmed” for unreadable/rejected attempts. A replaced entry is a normal skip, not proof that the application erased its secret. Never say “cleared” solely because the platform call returned. Source-owned mnemonic or unsupported legacy paths must first meet their separate security constraints before any success wording applies.

## Diagnostics and evidence

Only allowed fixed labels, numeric statuses and non-identifying error classes may be emitted. Exclude secrets, raw/encoded RP/user associations, credential IDs and keyed lookup tokens from messages, tags, causes, attached values and fallbacks. Preserve emission-to-output evidence for configured destinations and startup. Heuristic scrubbing adds defense, not permission to emit prohibited values.

Use [data-model.md](../data-model.md) for records and status semantics and [quickstart.md](../quickstart.md) for procedures. Clipboard outcome and verification result are separate: demonstrated correct handling of an accepted platform limit can pass the scoped behavior check while removal remains unknown. Unexecuted or unusable checks remain Unverified; wrong behavior remains Failed. No report may promote an attempted clear into an observed removal.

Define a frozen product candidate by its commit and tree, including the synchronized product, policy and register files in review scope; bind builds and runtime evidence to that candidate. Store the subsequently produced review and disposition as separate evidence records referencing that identity, so recording the review does not require a self-referential commit. The reviewer must receive the final pre-review evidence package and its hashes. Record any later delivery commit and compare it with the frozen candidate: evidence/disposition-only additions may be recorded separately when they do not alter reviewed product or policy scope; any changed reviewed material or changed product/build requires a new candidate, impact assessment, refreshed affected evidence and renewed independent review before acceptance. Do not imply an evidence-only exception covers changed product behavior or policy.

Publish sanitized revision-bound findings and hashes; retain synthetic raw heaps only in controlled storage with reviewer access while cited. Full acceptance requires reconciled source coverage, required behavior/runtime evidence, resolution of forbidden retention, documented provider limitations and independent security review of the assessed candidate. Implementation completion and release acceptance remain separate. Historical review fingerprints and old 60-second results retain their original scope.

## Independent synthetic clipboard observer

Implement `app/src/androidTest/AndroidManifest.xml` with a test-only exported `com.chimali.security.ClipboardObserverActivity` in process `:clipboardObserver`, implemented at `app/src/androidTest/kotlin/com/chimali/security/ClipboardObserverActivity.kt`. It must use Android SDK APIs only so it can launch directly from the installed test APK without target-process instrumentation. No observer component is added to production manifests or release artifacts. The separate test package/process must survive a force-stop of the target package; verify this explicitly before its evidence is eligible.

Implement `tools/security/run-clipboard-observation.ps1` as the serialized host controller. Inputs: explicit serial, target package, installed test package/activity, synthetic fixture/run ID, case, and controlled output directory. Validate actual package/PID separation and synthetic-state prerequisites; never discover or dump personal contents. For a background/death case, start the test activity via `adb shell am start -n <test-package>/com.chimali.security.ClipboardObserverActivity`, intentionally giving it focus while the target remains background/stopped. The activity reads description metadata only and returns JSON records containing run/case ID, elapsed observation time, marker-match/replaced/inaccessible classification, focus/lock state and capability-control result. It must never read/coerce clip text or emit marker contents or unrelated descriptions.

Keep target and observer receipts in separate controlled files, copied only from the declared synthetic test state; use non-content target attempt/schedule events for the tested operation. A process-death case must have a target-ready barrier containing the scheduled receipt before termination, and must not relaunch target instrumentation afterward. The controller verifies target PID absence and observer PID liveness before sampling. Foreground target checks use target-side probes rather than focusing the observer and accidentally changing the condition. Locked-state evidence remains Unverified unless its non-content controls demonstrate the relevant behavior without unlocking. The observer exposes no API granting clipboard access while locked/backgrounded. Implement `app/src/androidTest/kotlin/com/chimali/security/ClipboardObserverIsolationTest.kt` and a controller preflight proving package/process separation, no target restart, surviving target termination and metadata-only output before counting lifecycle cases.

### Synthetic token handoff

For isolated test builds only, the host controller generates a fresh random non-secret expected token for each run and streams the same value over standard input into two fixed-name, app-private per-run files: one in the synthetic target package and one in the test package, using verified `adb shell run-as` access. Use a declared synthetic debuggable target/test build; if either package cannot be accessed this way, the case is Unverified. Validate the run ID before deriving either fixed path, restrict host/device file access, and never place the token in shell arguments, logs, sanitized JSON or retained reports. An instrumentation-only token-source override reads the target-private file, injects its value into the target clipboard owner before the synthetic copy, and removes that target file immediately after reading. The normal production token source remains random and has no exported test setter, IPC endpoint or production-build override. The observer reads its own test-package private file; it cannot read the target's private file.

The target-ready barrier contains only the run ID, receipt generation, copy-call time window, derived publication time and schedule; it is emitted after the override supplied the token and the clipboard write returned. The controller validates that the derived publication time lies within the call window and that the schedule is exactly publication plus 30,000 ms. Before terminating the target, the controller verifies that the observer's expected-token file is readable and that a positive synthetic control produces `marker-match`; a deliberately different token must produce `replaced`. The observer compares only the description-extra token against its private expected token and emits classifications, never token contents or clipboard text. Missing injection, unreadable private storage, absent controls or process-isolation failure makes the case Unverified.

After the primary observation, the harness may remove its synthetic clip only through the separate observer's `clear-if-owned` mode: it re-reads the current ownership token and calls `clearPrimaryClip()` only when it still equals the run's expected token. Replaced, absent or unreadable ownership is skipped. The Android clipboard API does not provide an atomic compare-and-clear operation, so an external replacement can still race between this check and the clear call; retain that limitation explicitly. This test-only cleanup is never counted as the app's automatic/manual cleanup result. Delete the exact per-run files on both packages in teardown, including failure paths, after observations are complete; retain only sanitized results and hashes. Separately test the unmodified production random-token source; the deterministic synthetic injection is not evidence of its randomness. The token is a non-secret correlation value, not an authentication boundary; metadata replay limitations remain.

The host controller distinguishes case-specific outcomes. A foreground `scheduled-attempt` starts from a focused, metadata-confirmed synthetic copy with matching readable ownership, so it requires `ClearRequestSubmitted`; a known terminal skip or wrong deadline is a Failed behavior assertion, while a missing/unreadable result remains Unverified. An `app-switch` may correctly produce `SkippedOwnershipUnavailable` when background clipboard ownership cannot be read; the controller must retain that skip, run the independent observer, and report the observer classification separately without claiming removal. `SkippedReplaced` is accepted only when the metadata-only observer corroborates `replaced`. If the observer sees the current synthetic marker, test teardown may then use `clear-if-owned`; its outcome remains distinct from the app's result. A valid guarded skip is not a controller failure, even when the synthetic marker remains after its due time.
