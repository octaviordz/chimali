# FIDO SQLDelight generated-row signatures

- **Scope:** `Fido2Database.sq`, the PasskeyCredential/RelyingParty/UserConsentRecord schema/query files, current SQLDelight generated row types, DAO binding paths, and `EntityMappers` cleanup paths.
- **Revision:** Dirty exploratory worktree based on `78812e4d0a2d4ff422e03cd71611d6eb4ab4c57`; generated output is from the current worktree build and is not frozen-candidate evidence.
- **Observed schema-to-generated signature:** `Passkey_credential` represents `rp_id`, `rp_name`, `user_id`, `user_name`, `user_display_name`, indexes, and `encrypted_metadata` as `ByteArray` or nullable `ByteArray`; the TEXT `credential_id`, `id`, `aaguid`, `derivation_profile`, `public_key`, and label fields are `String`. `Relying_party` uses `ByteArray` for `id`, `name`, and encrypted metadata, and `String?` for `icon_url`. `User_consent_record` uses `ByteArray` for `rp_id` and its index, and `String?` for credential ID, device ID, IP address, and user agent.
- **Application-owned lifecycle:** Credential and relying-party DAO write buffers are cleared in `finally` after the synchronous SQLDelight bind call; consent insertion clears RP bytes and its lookup-token buffer in `finally`. Row hydration clears mutable identifying BLOB arrays in `EntityMappers`; repository flow owners clear rows after mapping and rejected emissions. The generated types are data classes and their generated `copy()` semantics are shallow for arrays; source search found no production row-copy use. Host tests do use row copies as synthetic setup, and those fixtures remain test-owned.
- **Limitations:** This is source/build-output inspection only. It does not establish SQLDelight driver/native copies, SQLite page/WAL/journal cleanup, backup behavior, current release encryption settings, immutable consent TEXT retention, or heap-root behavior. These remain open under T005/T006/T007/T012/T015/T039.
- **Conclusion:** The generated signatures are now explicitly mapped to their schema owners. No source change was justified by this inspection; driver and immutable-TEXT ownership are unresolved rather than assumed clean.
