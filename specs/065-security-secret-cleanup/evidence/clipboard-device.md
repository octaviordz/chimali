## Emulator clipboard description-extras flakiness investigation (2026-11-20, post-reboot)

After the API 35 emulator (`emulator-5554`) rebooted (~10:43 local, uptime confirmed at investigation time), the candidate-bound emulator extended-case attempts `sec065clip20261120q` (clipboard-replaced), `sec065clip20261120s` (manual-clear), `sec065clip20261120t` (repeat-copy) and `sec065clip20261120u` (clipboard-replaced) all returned `Unverified` at the observer positive-control stage: `capabilityControl=replaced` and `classification=replaced` even for `control-match`, meaning the observer's own `setPrimaryClip` + immediate `getPrimaryClipDescription` read-back did not observe the `TOKEN_KEY` description extra it had just written.

| `probe05` | `2222…` (new token) | marker-match | marker-match | extras visible again |

Sanitized probe records retained at `D:\temp\sec065-clip-candidate\clipboard-observer-probe0{1..8}.json` (SHA-256 `3F9A6451…`, `B69E82E3…`, `35E33053…`, `C6BE65BA…`, `C407DE1F…`, `10E3C13F…`, `35858071…`, `A4F5AFE2…` respectively; outside Git, alongside the harness observation JSONs). Tally: 6 of 8 direct probes observed extras consistently; probe03 read a stale prior clip and probe04 showed the control-internal read succeeding while the outer re-read lost extras — intermittent, not deterministic.

**Assessment:** this is an emulator/platform clipboard-service behavioral defect in `ClipDescription` extras persistence on immediate re-read — not application behavior (2 of 8 direct probes defective, yet all five harness control attempts failed, so the defect rate under harness timing may be higher). It plausibly explains the earlier candidate-bound emulator scheduled-attempt failures (`SkippedReplaced`/`Unconfirmed` across runs `sec065clip20261120a`–`f`, `r`) and the extended-case Unverified results, since the audit harness carries its ownership token in description extras. Physical cohorts (ASUS API 35, Mi A2 API 29, Motorola API 33 exploratory) consistently preserved extras and are unaffected; the production `AndroidClipboardManagerService` ownership token uses the same extras mechanism, so physical-device evidence remains the authoritative signal. Emulator clipboard evidence should be treated as capability-limited for extras-dependent assertions until the platform defect is root-caused; no product change is indicated by this investigation. T027 remains open.
