# Credential read flow downstream exception boundary

**Finding:** SEC065-FIDO-OWNER-004
**Date:** 2026-11-17
**Candidate:** Dirty exploratory worktree based on `78812e4d0a2d4ff422e03cd71611d6eb4ab4c57`

Credential read/search flows previously caught `android.database.SQLException` around both DAO row acquisition and downstream emission. A consumer that raised the same exception type could therefore be logged as a database read failure and silently converted into an empty completion. The catch boundary now covers only DAO flow collection (`first()`); conversion, filtering and downstream emission execute outside it. Each acquired row list remains protected by `finally`, and `emitOwnedCredential` erases an unaccepted model before the exception propagates.

The same broad-catch defect existed in credential summary hydration: a `SQLException` from the summary ownership observer was treated as an empty database result. Summary acquisition now catches SQL failures only around DAO collection and keeps the existing malformed-query validation fallback at that boundary. Mapping validation remains a typed error, while observer failures propagate; staged summaries and all source rows are erased from `finally` when ownership transfer does not complete.

`CredentialRepositoryImpl.updateRelyingParty` also caught `SQLException` across both the caller-supplied update function and the DAO write, converting callback failures into database errors. The catch now wraps only the DAO update. A synthetic SQL exception from the callback propagates as the same instance, the borrowed RP owner is erased in the method's `finally`, and no DAO update occurs.

`getCredentialById` previously caught `SQLException` around both the DAO lookup and row hydration, which could convert a provider/mapper failure into a missing credential. SQL handling now covers only DAO lookup. The paged and full RP batch methods had the same broad boundary; their catches now cover only DAO acquisition and their existing `finally` blocks erase all source rows and partial model owners. `getCredentialsByIds` no longer wraps its caller-owned batch cleanup in a database catch, and creation validation now catches SQL failures only during DAO flow acquisition. Synthetic SQL failures from `PublicKeyDecoder` propagate unchanged after cleanup on direct-ID, paged, full-RP batch, ID-set, and creation-validation paths.

The `search propagates database-shaped downstream failure after erasing owners` regression throws a synthetic `android.database.SQLException` from the collector, verifies the same exception instance propagates, and confirms both the emitted credential's text owners and source row byte arrays are zeroed. `summary observer SQLException propagates and erases staged summary and source row` verifies the summary callback exception propagates as the same instance and staged summary/source-row buffers are zeroed. `update relying party propagates database shaped callback failure and erases borrowed owner` verifies same-instance propagation, RP owner erasure, and zero DAO updates. Parameterized direct-ID, ID-set, creation-validation, page and RP-batch mapper tests verify same-instance propagation and row cleanup. The focused `CredentialManagementTests` group passes 45 cases; the outer `CredentialRepositoryImplTest` class passes 11 cases. The complete FIDO host suite passes 1,326 tests across 172 reports with zero failures/errors/skips; FIDO KtLint passes.

This is host/source evidence for application-owned row/model cleanup and exception propagation. Database/provider copies, all production consumer terminal events, renderer snapshots, joined external borrowers and heap roots remain open under T006/T012/T015.
